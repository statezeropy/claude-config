# Service conventions

These are decisions, not knowledge. Each has several defensible answers; this is the one used in
every project so that two services written a year apart still look alike. Library mechanics —
how autogenerate works, what a Redis hash costs — are deliberately absent: read the installed
version's source and docs for that (`python-standards` §2).

## PostgreSQL schema

| Need | Use | Not |
|---|---|---|
| timestamp | `timestamptz` — `DateTime(timezone=True)` in SQLAlchemy | naive `timestamp` |
| free text | `TEXT` | `VARCHAR(n)` unless the length is a real business rule |
| primary key | `BIGINT` identity; `UUID` only when ids are minted outside the DB | `INTEGER`, `SERIAL` |
| semi-structured | `JSONB` | `JSON`, `TEXT` holding JSON |
| exact amounts | `NUMERIC(p, s)` | `FLOAT`, `REAL` |

- Tables plural snake_case (`user_profiles`), columns snake_case, booleans read as predicates
  (`is_active`), timestamps end in `_at`, dates in `_on`.
- **Every constraint has a name**, set once on the metadata so autogenerate never emits an
  unnamed one — an unnamed constraint cannot be dropped in `downgrade()`:

  ```python
  NAMING_CONVENTION = {
      "ix": "ix_%(column_0_label)s",
      "uq": "uq_%(table_name)s_%(column_0_name)s",
      "ck": "ck_%(table_name)s_%(constraint_name)s",
      "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
      "pk": "pk_%(table_name)s",
  }

  class Base(DeclarativeBase):
      metadata = MetaData(naming_convention=NAMING_CONVENTION)
  ```

## Alembic revisions

- Message is lowercase imperative and names the change:
  `alembic revision --autogenerate -m "add user_profiles table"`.
- `alembic.ini`: `file_template = %%(year)d%%(month).2d%%(day).2d_%%(rev)s_%%(slug)s` so files
  sort chronologically in a listing.
- Read every autogenerated file before committing. Autogenerate emits drop+create for a rename
  and misses server defaults and enum value changes.
- `downgrade()` is implemented, never `pass`. If a step is truly irreversible, the docstring says
  so and why.
- A revision that has run anywhere — the dev server counts — is never edited. Add a new one.
- Schema and data migrations are separate revisions. Data migrations use `op.execute()` with
  plain SQL, never ORM models: models drift, a migration must not.

## Redis keys

- `namespace:id:attribute`, colon-separated, lowercase: `user:123:profile`,
  `cache:product:456`, `lock:order:789`, `queue:emails:pending`. Namespace first so
  `SCAN user:*` and per-prefix TTL policy work.
- When several services share one instance, the service name is the outermost namespace:
  `billing:user:123:profile`.
- **Every key that is not a permanent record gets a TTL at write time** (`SET … EX`,
  `SETEX`). A key without a TTL is a memory leak with a delay.
- One hash per entity (`HSET user:123 name … email …`) rather than N string keys.

## Tests

```
tests/
├── conftest.py        session-wide fixtures: app, engine, settings override
├── unit/              no I/O, no network — seconds
├── integration/       real DB/Redis from docker compose; own conftest.py
└── e2e/               Playwright against the running stack
```

- Markers `unit`, `integration`, `e2e`, `slow` are registered in
  `python-standards/templates/pyproject-tooling.toml`; `--strict-markers` rejects any other.
- Files `test_<module>.py`, functions `test_<behaviour>`:
  `test_login_rejects_expired_token`, not `test_login_2`.
- CI runs `unit` and `integration` on every push and PR; `e2e` on `main` and on tags.

## CI workflows

- One concern per file under `.github/workflows/`: `ci.yml` (lint, type, test on push/PR —
  `python-standards/templates/ci.yml`), `release.yml` (on `v*` tags; `git-workflow` makes the
  tag the production trigger), scheduled jobs in their own file.
- A CI step runs **the same command the developer runs** (`uv run ruff check .`), never a
  CI-only variant. If it passes locally it passes in CI, and vice versa.
